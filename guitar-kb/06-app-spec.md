# Guitar Trainer — App Build Spec (v1)

This is the build brief. The **content** is defined in `catalog/` (see `catalog/SCHEMA.md`) and the curriculum docs `01`–`05`. This doc defines the **app**: stack, screens, session flow, grading, on-device data, and build order.

## 1. Ground rules
- **Single user, personal use, offline.** No accounts, no backend, no analytics, no ads. All data stays on the phone.
- **Platform: a website (installable web app) on GitHub Pages.** Opened in Chrome on the **OnePlus Open** (foldable, Android 16+) and added to the home screen, where it runs full-screen like an app. Decided 2026-11-21, replacing the native Android plan: no Android Studio, no app store, and updates appear on the next reload.
- **Hosting:** a public GitHub repo serving GitHub Pages, because a free account can't publish Pages from a private repo. The repo holds code and facts-only catalog data, never lyrics. Progress never leaves the phone. Claude-hosted artifact links can't be used, because they block microphone access.
- Layouts must work on both the cover screen and the inner screen (§3a).
- **Catalog is read-only.** It ships as `web/public/catalog/*.json` and is regenerated by the Python build scripts. The app never edits it. User progress is keyed by catalog IDs, which are stable and never reused.
- **Copyright.** Song outlines stay facts-only. The app has no file import or upload (decided 2026-11-23), so no charts or set lists enter the app.

## 2. Tech stack
| Layer | Choice | Why |

| UI | **Preact** + Vite (small, fast, React-style components) | Light enough for a phone; no heavy framework |

| DSP | `dsp.js` (YIN pitch, spectral-flux onsets, peak-based chroma + chord verify), proven in M0 and kept identical to `m0/src/dsp.js` (a test checks); runs on the main thread | Shared by graders, tuner and games |

## 3a. Foldable layouts (OnePlus Open)
Use CSS breakpoints on window width (cover screen < 600 px, inner screen ≥ 600 px) and, where Chrome exposes them, the Device Posture API and viewport-segment media queries for tabletop. Never hard-code a screen size.

| Posture | Layout |
|---|---|
| **Folded (cover screen, compact width)** | Single pane. Bottom navigation. Quick-use mode for church: tuner, metronome, and Song view in large type |
| **Unfolded (inner screen, medium/expanded width)** | Two panes with a navigation rail. Lesson: text on the left, live diagram/tab/attempt runner on the right. Song view: chart on the left, chord diagrams for every chord in the chosen key and capo on the right. Path: track map with lesson detail beside it |
| **Half-folded on a table (tabletop), when the browser reports a folded posture with a horizontal hinge** | Top half: chart, tab or tuner needle, readable from playing position. Bottom half: controls (start/stop, tempo, section jump) |

**State must survive folding and unfolding.** In the browser a fold is a resize, not a reload. The audio engine, the running click and any attempt in progress live in one module-level engine, never inside a screen component. A Screen Wake Lock keeps the display on while practicing. Folding mid-attempt changes the layout only; it doesn't restart the attempt or drop audio.

## 3b. Tuner and metronome in every lesson
Every Lesson screen (and the Song view) has a **tool bar** with two buttons: **Tuner** and **Metronome**. They're the same engine as the Tools screen, not separate copies.

- **Metronome mini-player.**
  - Opens as a compact bar pinned to the bottom of the lesson: play/stop, BPM −/+, tap tempo, meter, subdivision, volume.
  - **Pre-set from the lesson:**
    - The current tempo-ladder BPM for the lesson's exercise; else `pass_criteria.bpm`; else the song's BPM; else 80.
    - Meter and subdivision come from the exercise, rhythm pattern or song.
    - A "target" chip jumps straight to the pass tempo.
  - **Keeps running** while you scroll the lesson, open a diagram or switch to another lesson. It stops only when you stop it or leave lessons and songs entirely.
  - Changing the BPM here is just practice. It never changes the tempo ladder. Only graded attempts move the ladder.
- **Tuner sheet.**
  - Opens as a half-height bottom sheet over the lesson: needle, note name, cents, plus string buttons for standard tuning. Swipe down to close.
  - It shows the input route in use (phone mic or USB). Folded it's large-type; unfolded it docks in the right pane next to the lesson text.
  - Tuning is noted per practice session, so the app knows you've tuned.
- **Before an audio-graded attempt** (`pitch`, `timing`, `chord_accuracy`, `changes_per_min`): if you haven't used the tuner in this session, the attempt runner offers a one-tap "Quick tune" first. You can skip it.
- **During an attempt** the attempt runner owns the click at the exercise's tempo. The mini-player pauses and picks back up afterward at its previous BPM. The tuner sheet is hidden during attempts.
- **Tabletop posture:** tuner needle or metronome beat light on the top half, controls on the bottom half.

## 4. Session flow
1. **Today** builds the queue (`buildQueue` in `web/src/practice.ts`): warm-up (F.05, once unlocked) → due reviews, oldest first (1 in 10 min, up to 2 in 20 min, up to 3 in free) → current lesson per visible track, passed-once first (at most 1 / 2 / all) → an ear quiz in 20 min when unlocked. Songs are not queue steps; the song of the week has its own box and changes on Monday.
2. Each item opens its lesson, where the **Attempt runner** runs. An attempt = one measured run against the lesson's `pass_criteria`.
3. The result is written to `attempt` and the lesson state and review schedule are updated in the same transaction; the tempo ladder is saved by the runner.
4. A **practice session** groups the attempts of one sitting. It closes after 30 minutes without activity, including time in the background; this is checked when the app starts or comes back, and before anything uses the session.

## 5. Progress rules (exact)
**Lesson states:** `locked → available → in_progress → passed`. "Review due" is a flag on a passed lesson, not a state.
- **Unlock:** every `prereqs[]` lesson is passed **or passed once** (decided 2026-11-21: waiting a day after a first pass stalled day one). Tracks A/ER/EL unlock once every F lesson is passed at least once. The second-day pass still completes a lesson and starts its reviews. Lessons passed once *today* drop out of today's queue. Track choice in Settings hides the tracks you didn't pick (they stay unlockable). T lessons follow their own `prereqs`.
- **Pass:** the criterion is met **at target tempo** on **2 different calendar days**. The first success sets `first_pass_day`; the second sets `passed_day`.
- **Reviews** (as the code does it, `applyAttempt` in `web/src/progress.ts`; `review_days` = 1, 3, 7, 14, 30):
  - Passing the lesson schedules the first review 1 day later.
  - A review passed on a due day schedules the next one `review_days[i] − review_days[i−1]` days after **that day** (+2, +4, +7, +16). So with every review done on time they fall 1, 3, 7, 14 and 30 days after the pass; a late review pushes the later ones back by the same amount. (Note: this is not "`passed_day` + `review_days[i]`", as this spec used to say.)
  - A missed attempt on a due day restarts the schedule: next review tomorrow, then the same gaps again. The lesson stays passed and dependents stay unlocked.
  - After the last review (the 30-day step) the lesson is "mastered" and has no more reviews.
- **Tempo ladder** (for `timing`, and for `pitch` exercises that have a tempo):
  - Start at `round(0.65 × target_bpm)`. Graded attempts always run at the ladder tempo (no skip-to-goal); reviews and practice after passing run at the target.
  - **Clean** = criterion met at the current tempo. After 3 clean attempts in a row, add 4 BPM (capped at target).
  - **Fast track** = clean with mean error ≤ ½ `max_err_ms` and ≥ 97% of slots right. Adds 8 BPM straight away (capped at target), so a strong player isn't held at 65% for a dozen attempts.
  - **Sloppy** = mean error > 1.5 × `max_err_ms`, or detection rate < 80%. After 2 sloppy attempts in a row, subtract 8 BPM (floor: 50% of target).
  - Anything between clean and sloppy leaves the tempo unchanged.
  - Attempts below target tempo build the ladder but never count toward a pass.
- **Self-check lessons** pass when you mark them done on 2 different days. (Offering a recording to listen back to first is not built.)

## 6. Grading (one `Grader` per `pass_criteria.type`)
**Key design choice:** the app always knows what you're *supposed* to play. Every audio grader **verifies against an expected target** instead of trying to recognize anything open-ended. This is far more reliable on a phone mic.

| Type | Method | Score |
|---|---|---|
| `quiz` | Generated from `quizzes.json` templates; ear quizzes play synthesized audio (§9) | correct ratio ≥ `score`, and mean answer time ≤ `max_s` if set |
| `pitch` | YIN pitch tracker on the input; compare to the expected note from the exercise or the tuner target | `cents`: held pitch within ±cents for ≥ 0.5 s · `note_accuracy`: ratio of expected notes matched in order |
| `timing` | Spectral-flux onset detector; each onset matched to the nearest expected grid slot (`subdivision`) within half a slot; offsets corrected by the calibrated latency | mean absolute error ≤ `max_err_ms` **and** ≥ 90% of expected slots hit |
| `chord_accuracy` | Chroma vector per strum (12 pitch classes, averaged over 60–450 ms after each onset, cut short at the next strum), cosine similarity against the **expected** chord's template vs. the other chords and decoys in the exercise | ratio of **bars** (timed) or strums (own pace) heard right ≥ `ratio` |
| `changes_per_min` | Same chord verifier; counts correct strums that follow a strum of the *other* chord in the pair during a 60 s window | count ≥ `target`. No `pair` → run each pair from the lesson's `chord_changes` exercise, and all must pass |
| `self_check` | None. Optional recording + playback | user confirms |

**Fallback flag:** each audio grader except timing has a mode (Settings → Grading mode): `auto`, `assisted` (shows the detection, then you confirm or override), or `self`. Defaults (`web/src/grading/modes.ts`): pitch `auto`; octave shapes, double stops and both chord graders `assisted` until the audio check (§10) has been done on the phone. Lessons still work; assisted just asks you to confirm.

**Input routes:** phone mic · wired headset mic · USB audio interface (class-compliant; it appears in Chrome's input list). The mic is opened with echo cancellation, noise suppression and auto-gain **off**. Each route is calibrated separately (§7). **Bluetooth headphones are blocked for timing attempts**, because their 150–300 ms latency makes timing grades meaningless. The app shows a warning when Bluetooth output is active.

## 7. Audio engine
- **One `AudioContext`** (`latencyHint: 'interactive'`), created on the first tap; Chrome requires a user gesture.
- **Click scheduling** is sample-accurate: every click is an oscillator burst started at an exact `AudioContext` time (2600 Hz accent / 2000 Hz, 2 ms raised-cosine attack, 6 ms decay). A short look-ahead loop keeps the next ~200 ms scheduled. Timers never decide *when* a click sounds.
- **Capture:** an `AudioWorklet` posts 512-sample blocks tagged with `currentFrame`, so every input sample has an exact context time. A 10-second ring buffer feeds the analyzers. Missing frames are counted as capture gaps.
- **Analyzers** (from M0's `dsp.js`):
  - **Tuner:** YIN over 2048 samples.
  - **Onsets:** spectral flux at frame 1024 / hop 256. It ignores 1800–3200 Hz, so the click's speaker bleed isn't heard as a strum. During the count-in it learns the bleed level and applies that floor only around predicted click arrivals.
  - **Chroma:** spectral peaks from an 8192-point FFT, averaged over 60–450 ms after a strum, matched by cosine similarity against templates built from the actual voicing.
- **Latency:**
  - **Strum calibration** (in the app): a 4-click count-in, then 16 muted strums on the click. Gives the offset subtracted from every timing grade; stored per input route and per posture.
  - **Click bleed:** each click-timed attempt learns the bleed level and arrival time during its count-in. Pitch and chord attempts without a strum calibration use that measured arrival as the offset; timing attempts require the calibration.
  - **Loopback** (speaker → mic, 16 clicks, round-trip delay) is a test on the M0 audio page only. The app does not run or store it.
- **The engine API** exposes the subscribe/unsubscribe streams for blocks, pitch and onsets, plus start/stop for the click and capture. Graders only consume these.

## 8. Lesson content format (`content/{lesson}.md`)
Plain markdown plus embed tokens that the renderer swaps for live components:

| Token | Renders |
|---|---|
| `{{chord:G_4f}}` | Chord diagram from `chords.json` (or chords-db by name) |
| `{{shape:E_shape_major@3}}` | Movable shape placed at a fret |
| `{{triad:tri_321_G_root}}` | Triad diagram |
| `{{scale:Am_pent_pos1}}` | Fretboard scale diagram |
| `{{rhythm:S3_worship}}` | Strum grid with a play button |
| `{{exercise:EX_spider}}` | Exercise card: tab (with its tempo ladder), chord pairs or chord progression |
| `{{song:ID}}` | A public-domain song from `songs.json` (chords and lyrics) |
| `{{outline:MS_goodness_of_god}}` | Link to the Song view of a song outline |
| `{{tool:tuner}}` / `{{tool:metronome:bpm=80}}` | Inline tool launcher |
| `{{quiz:Q_note_names}}` | Inline quiz |

The web test suite (`web/test/progress.test.ts`, parser in `web/src/tokens.ts`) checks that every token references an existing ID. The catalog build script checks lesson assets.

## 9. Sound sources (no recordings)
- **Click:** synthesized (short sine burst or filtered noise); accent = higher pitch.
- **Chord/note playback:** Karplus-Strong plucked-string synthesis using the voicing's actual MIDI notes (`meta.json` tuning + frets), strummed at 15–25 ms per string. This powers ear quizzes, "hear this chord", and song chord playback.
- **Later:** a simple drum-loop generator (kick/snare/hat patterns per strum grid) for groove practice.

## 10. Audio feasibility test (M0, built)
The M0 page is a single file (`m0/index.html`) with seven tests. Results are kept per input and posture and copied out with one tap. Its DSP passed synthetic tests in Node and an end-to-end check in headless Chrome with a fake microphone. These synthetic results:
- **Tuner:** worst error 0.3¢ on plucked notes E2–E5.
- **Onsets:** about 2 ms error, with no false triggers from the click.
- **Chord verify:** 100% on synthetic G-family strums.

Real guitars and phone mics will be harder; the table below is filled from Connor's phone.

| Check | Pass bar |
|---|---|
| Tuner accuracy vs reference tones through the speaker (or a known-good tuner) | ±2 cents, stable reading within 300 ms |
| Click stability (speaker → mic loopback, 2 min) | inter-click jitter < 1 ms, no capture gaps |
| Round-trip latency, per input route and posture | measured and repeatable within ±5 ms |
| Onset timing after strum calibration | strummed eighths at 80 BPM: mean error ≤ 15 ms, ≥ 90% hit |
| Chord verification, phone mic at ~1 m, acoustic | right chord vs another chord from the same family: ≥ 90% across the A.02 G-family chords |
| Kemper over USB-C: does Chrome list it as an input, and on which channels? | yes/no + channel map. If yes, chord verification on a clean tone ≥ 95% |
| Fold/unfold while the click and capture are running | no capture gaps, click shift < 5 ms |
| Mic choice: folded vs unfolded | log which mic and settings Chrome uses in each posture, and whether latency changes |

If chord verification misses its bar, ship with `assisted` mode for those graders and revisit later.

## 13. Decisions on open items
- **Phone:** OnePlus Open, in Chrome. Browser audio latency varies by phone, so M0 measures it on the device: run the checks folded and unfolded, with each input route.
- **Electric input:** phone mic is the baseline, and every lesson must work with it. The Kemper Profiler Rack MK2 has a USB-B port that works as a USB audio interface, so M0 also tries it with a USB-B → USB-C cable:
  - Android only supports class-compliant USB audio. If Chrome doesn't list the Kemper as an input, drop this route. No extra purchase is needed.
  - If it works, grade from a clean or dry signal. Delay and reverb smear onsets and chroma. Pick the dry channel if the Kemper's USB channels include one; otherwise use a clean rig with effects off for graded attempts.
  - The Kemper's 8 USB channels may show up as a multichannel input. The engine must let you choose which channel to analyze.
- **Import:** none. The app has no upload, import, backup or restore controls (decided 2026-11-23).
