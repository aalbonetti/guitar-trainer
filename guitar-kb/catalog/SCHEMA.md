# Content Catalog Schema (v1)

The catalog is the app's content database, stored as JSON files in `catalog/`. It's generated by `build_catalog.py` (song outlines and Song Run levels by `build_song_outlines.py`). `build_catalog.py` also **checks the music data**: every chord voicing is checked note-by-note against its chord formula (including bass note; the 3rd or sus note, any 7th, the 9th of an add9 and the b5 of an m7b5 must be there), every movable shape is checked at frets 1–12, every scale position against its scale formula, and the triads and octaves are checked too. Every lesson's prerequisites and asset references are checked to exist, and the prerequisites are checked for cycles. Every `quiz` lesson must have a quiz asset. Neither script writes a file unless all of its checks pass.

## Conventions
- Per-string arrays have 6 values, ordered **string 6 → string 1** (low E first). `-1` = muted, `0` = open.
- Standard tuning MIDI: 40 45 50 55 59 64. A fretted note's MIDI value = open string + fret.
- IDs are stable strings and are never reused. Lessons reference assets by ID.
- Scale position numbers follow the minor-pentatonic box numbering. The G major pentatonic "pos2" is the classic major box rooted at string 6, fret 3.

## Files
† marks a **build/doc-only** field: it's generated for the build checks or as documentation, and the app doesn't read it.

| File | Contents |
|---|---|
| `meta.json`† | `{schema_version, string_order, muted, tuning{standard[], midi[]}}`. Copied with the catalog but not loaded by the app |
| `tracks.json` | `{id, name, instrument: acoustic\|electric\|both, order, requires?[]}` |
| `lessons.json` | `{id, track, title, prereqs[], pass_criteria, assets{chords?, shapes?, triads?, scales?, rhythm?, picking?, exercises?, songs?, quizzes?}, content†, review_days[]}`. The app loads `content/{id}.md`. A quiz counts toward a `quiz` lesson when it's in that lesson's `assets.quizzes` (one quiz can serve several lessons) |
| `chords.json` | `{id, name, root†, quality†, bass?†, frets[6], fingers[6], barre?{fret, from†, to†}, tags[], alt_of?†}` |
| `shapes.json` | `movable_chords[] {id, quality, root_string, offsets[6] (null=muted)}`, `triads[] {id, root, quality, strings[], frets[]}`, `octaves[]† {low_string, high_string, fret_offset}` |
| `scales.json` | `{id, name, root, kind, position, frets[6][], movable}` |
| `rhythm.json` | `strumming[] {id, name, meter, grid, steps[] (D/U/-/X, one per grid slot), accents[] (step idx), swing†, level†, palm_mute?, notes?†}` · `picking[] {id, name, meter, grid, steps[], notes?†}`. Each picking step has one key, `p\|i\|m\|a`, whose value is a string number or `'root'`/`'alt_bass'`. A step may also carry `fingers?`† : the **string numbers** the fingers pluck together with that step's thumb note (a pinch), so `{p: 'root', fingers: [3,2,1]}` is the bass plus strings 3, 2 and 1. The app's pick grid shows only the first key. |
| `exercises.json` | Common: `{id, name, type, meter?, notes?}`. `type: tab` → `{tempo?{start, target, step}, events[] {beat, string, fret, dur, tech?, bend?}, chords?[]†, fx?{}†, loop†}`. Events on the same beat sound together (octaves, double stops). `tech: harmonic` sounds above the open string (fret 12 = +12, 7 = +19, 5 = +24); `tech: bend` + `bend` (semitones) is bent up from the fret to fret + bend; `tech: swell` is a volume swell (no pick attack). No `tempo` = played at your own pace · `type: chord_changes` → `{pairs[][], duration_s, target_per_min, voicings}` · `type: chord_progression` (`chord_accuracy`) → `{meter, pace: timed\|own, bpm? (fixed click) \| tempo? (ladder, lesson has bpm), beats_per_chord? (timed), strums_per_chord? (own pace), pick: only\|random\|choose (which variant: the one, a key named at random, or you choose), show: chords\|numbers, variants[] {key, capo, chords[] (one per bar/box), numbers?[], shapes?†, label, names? (chord names spelled for the key)}, decoys?[] (chords the lesson warns against, e.g. Fmaj7 for F), focus?[] (only these chords are graded, each must reach the ratio on its own), voicings}`. **Chord refs** in pairs/variants are a chord id, a triad id or `shape@fret` (`A_shape_minor@7`); `G\|G_4f` = either fingering counts. `voicings` is generated: `{ref: {name, frets[][] (each accepted fingering, without capo), where, root, quality, label? ('Bm (partial)')}}`, so graders build templates from the exact voicing (sounding pitch = fret + capo) |
| `songs.json` | `{id, title, words, tune, public_domain†, meter, key, tempo, pickup_beats†, level†, capo_options[]†, sections[] {name, bars[], numbers[]†, lyrics[]}, chords_used[]†, rhythm[]†, verify†}`. Public-domain only |
| `quizzes.json` | `{id, lesson (the lesson it mainly drills; the Daily Challenge uses it), type: generated\|ear, prompt (template), params{}}`. The app generates the questions |
| `games.json` | `{id, name, blurb, unlock_lesson, review_for[], modes[] (tap\|play), milestone†, levels[]}` (level fields in `07-games.md` §7). Song Run's levels (one per outline) are written by `build_song_outlines.py`, so always run both scripts in order |
| `badges.json` | `{id, name, blurb, rule{kind, game?, level?, mode?, stars?, keys?, accuracy?, min_calls?, positions?, gap_bars?, within_ms?, in_a_row?, streak?, days?}}` |
| `song_outlines.json` | Modern worship songs stored as **facts only**: `{id, title, artist, ccli, original_key, bpm, meter, chart_key, sections[] {name, chords_in_chart_key[], numbers[]}, capo_options[]† {shapes, capo}, practice_for[] (lesson ids), links{songselect}, sources†{meta, chords}, chords_verified†, notes, content_policy†, weekly_pool}`. No lyrics, melody, or signature riffs. Generated by `build_song_outlines.py`, which converts every chord to Nashville numbers and flags anything outside the key. `weekly_pool` marks the songs used for the song of the week, Set Ready and Call the Number songs mode |
| `setlist.json` | Not part of the published catalog. A personal set list (local, gitignored, never published); one saved on the phone by an earlier version still takes priority over `weekly_pool` |
| `content/{lesson}.md` | Teaching text for all 48 lessons (in `guitar-kb/content/`): markdown plus one-per-line embed tokens such as `{{chord:G_4f}}`, `{{chords:G_4f,Cadd9}}`, `{{shape:E_shape_major@3}}`, `{{outline:MS_…}}` (format in `06-app-spec.md` §8). The web test suite checks every token ID |

## pass_criteria types
| type | fields |
|---|---|
| `changes_per_min` | `target`, `pair?` (one of the lesson's `chord_changes` pairs; without it every pair runs, and all must pass) |
| `timing` | `bpm`, `subdivision` (4/6/8/16), `max_err_ms`, `bars` |
| `pitch` | `cents?` (hold each target within ±cents for 0.5 s: `scope: all_strings` = the six open strings, else the lesson's bend exercise) · `note_accuracy?` (ratio of the exercise's notes matched in order) · `bpm?` (played to a click; tempo-ladder target, the exercise tempo must be 65% → bpm) · `any_octave?` (a note counts in any octave; default exact octave) |
| `chord_accuracy` | `ratio`, `bpm?` (played to a click on a tempo ladder; otherwise the exercise's `bpm` or your own pace) |
| `quiz` | `score`, `max_s?` |
| `self_check` | (none; optional recording) |

## On-device data (IndexedDB): user progress
The catalog is read-only. Everything the app learns about the player lives in IndexedDB in Chrome on the phone (database `guitar-trainer`, version 6, through the hand-written wrapper in `web/src/db.ts`; the app asks for `navigator.storage.persist()`), keyed by catalog IDs. Rules for how lesson rows change are in `06-app-spec.md` §5. Times (`at`, `*_at`) are epoch milliseconds; `day` is the local calendar date `YYYY-MM-DD`. Upgrades only create stores, so existing rows are kept.

| Store | Key | Fields |
|---|---|---|
| `lesson_progress` | `lesson_id` | `state (locked\|available\|in_progress\|passed), first_pass_day?, passed_day?, review_index, next_review_day?, mastered, updated_at`. `review_index` points into the lesson's `review_days[]` |
| `attempt` | `id` (auto); index `lesson_id` | `session_id (string\|null), lesson_id, criterion_type, grader_mode (auto\|assisted\|self), score (0–1), met_target, at_target_tempo, metrics_json, event (none\|first_pass\|passed\|review_passed\|review_failed\|mastered), day, at`. Written by `recordAttempt` (`progressStore.ts`). `metrics_json` is a JSON string whose keys depend on the grader (quiz: `correct, total, meanS`; Arcade review credit: `via, level, stars`; self-mark: `{}`; audio graders: tempo, input route, offsets and per-type detail) |
| `practice_day` | `day` | `active_s?` (practice seconds that day; a day counts with ≥ 300 s. Older rows without it count as practiced) |
| `quiz_item_stats` | `[quiz_id, item_key]` | `seen, correct, last_seen_at, ms_sum?`. Weights questions toward misses. Fretboard heatmap rows use `quiz_id = 'arcade:fretboard'`, `item_key = 's5f7'`, with `ms_sum` |
| `kv` | `key` | `v`. Tempo ladders: `key = 'ladder:{lesson_id}'`, `v = {bpm, clean, sloppy}` |
| `calibration` | `key` (`input_route\|posture`) | `input_route, posture (folded\|unfolded), offset_ms, spread_ms, method ('strum'), measured_at`. The offset is subtracted from timing grades |
| `practice_session` | `id`; index `day` | `started_at, ended_at, day, routine ('10'\|'20'\|'free'), total_s, tuned_at?, items, items_done, attempts, passes`. Written when a session ends |
| `imported_chart` | `id` | Unused. Chart import was removed (the app has no file import); the store stays so old data still loads |
| `game_run` | `id` (auto); index `game_id` | `session_id, game_id, level_id, mode (tap\|play), score, accuracy, max_combo, max_streak, stars, duration_s, misses_json, extra_json, grader_mode, counted_review_for, at` |
| `game_best` | `key` (`game\|level\|mode`) | `game_id, level_id, mode, best_score, best_stars, ghost ([[second, score], …]), at` |
| `xp_ledger` | `id` (auto) | `at, source (game\|lesson_pass\|review\|daily\|pb), ref_id, xp` |
| `service_day` | `day` | "Played a service" days |
| `badge` | `badge_id` | `earned_at` |
| `daily_challenge` | `day` | `items_json, created_at, completed_at?` |

The streak and its freezes are recomputed from `practice_day` and `service_day` (`web/src/streak.ts`); there is no streak store. Small settings and the open practice session (`gt_session`) live in localStorage under `gt_*` keys.

**Catalog updates:** lesson states are computed from the current catalog and `lesson_progress`, so new lessons need no rows. Never delete history: rows for IDs that disappear are kept. `exportAll`/`importAll` remain in `db.ts`; no screen calls them (`?sim` tests use `importAll`).
